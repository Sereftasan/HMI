## 1. Please review first: changes that affect how the machine behaves

| # | Change | Why | Where |

## 4zf. The Dashboard's tables were slow: what it was, and the fix (2 October)

3. **About a database and codes for the HMI's log**, as you suggested: with the numbers above it would not make the page noticeably faster now - the text files are read at about 100 000 lines a second and kept in memory, and the machine's log is already a coded SQLite database. ## 7. Noticed, not changed (kept for later)

- MX Component: when a batch read fails, the per-address fallback (about 15 ms each) can exceed the 1 s wait on a page with many addresses, so one invalid address can make a station flap. Needs the hardware to tune.
- `Kaban.Core.csproj` lists `Data/Schema.sql`, which was not in the upload; Visual Studio fails if it is missing on disk.
- The machine executables have no App.config binding redirects, while Kaban.Core uses System.Text.Json 10 and its nine dependencies - worth confirming on a clean PC.
- `SimulationMonitorForm` reads simulated memory by reflection every 250 ms; `CylinderUnitHMI` (was FunctionUnitHMI) checks its help files on disk at every property set in the designer; `PlcAddressHelper.OffsetAddress` compiles a regex per call. All small.
- `BoundedDriver.Dispose` disposes the wrapped driver on the caller's thread while its worker may still be using it (it also unblocks a stuck socket, which is useful - left as is).
